# План доработки: экономия токенов и скорость работы агента с AutoCAD

Цель: агент (Claude через MCP) должен тратить меньше контекста на каждый шаг
и делать меньше шагов. Сейчас контекст расходуется на три вещи:

1. **Каталог инструментов**: описания и схемы, которые клиент загружает в
   начале сессии.
2. **Ответы инструментов**: JSON после каждого вызова, списки сущностей,
   скриншоты.
3. **Обходные пути**: лишние вызовы и большие скиллы там, где серверу не
   хватает инструмента (СПДС через AutoLISP, чтение переменных через `_OUT`).

План построен от этих трёх статей. Пункты 1–5 исходного списка Cowork вошли
в него. Порядок выбран по соотношению выигрыша и затрат.

## Живая проверка (AutoCAD 2026)

Всё новое проверяется одним прогоном `scripts/smoke_v17_com.py` (`AUTOCAD_MCP_BACKEND=com`). Скрипт
работает в своём новом документе и закрывает его без сохранения, а чертежи пользователя только
перечисляет. Режим `--headless` прогоняет те же шаги на ezdxf (проверено: все шаги проходят).

Цикл «действие → проверка» после этапа 2 (ezdxf, лист А3 с десятком объектов):
`drawing_diff_since` ≈ 40–80 токенов, `drawing_digest` ≈ 100 токенов, ответ на создание

Окно 120×60 мм при ширине 600 px — ≈ 240 токенов. Попутно исправлено: headless-рендер
был почти пустым (линии тоньше пикселя на тёмном фоне).

## Замеры (ветка `main`, v1.6.0, ezdxf, 2026-10-21)

> **Поправка после стенда.** Модель видит не весь JSON `tools/list`: клиент передаёт ей только
> `name`, `description` и `inputSchema`, без `_meta`, `outputSchema` и аннотаций. Видимый модели
> каталог полного режима занимает ≈ 57 тыс. токенов, а не 93 тыс. При этом схемы параметров
> весят больше описаний (136 тыс. символов против 96 тыс.), и главный рычаг — схемы.
> Цифры ниже — первичный замер всего JSON.

Токены оценены как `символы / 4` по JSON из `tools/list`. Для английского
текста это близко к реальному значению, для кириллицы значение занижено.

| Конфигурация | Инструментов | Каталог, ≈ токенов |
|---|---:|---:|
| `full` (по умолчанию) | 247 | **≈ 93 500** |
| `TOOL_PACKS=core` | 183 | ≈ 63 000 |
| `TOOL_PROFILE=lean` | 65 | ≈ 25 000 |
| `DISCOVERY_MODE=search` | 2 | ≈ 400 (но каждый шаг стоит поиска) |

Самые тяжёлые группы: `entity_*` ≈ 13 тыс. токенов, `drawing_*` ≈ 12,7 тыс.,
`arch_*` ≈ 7 тыс., `pid_*` ≈ 4 тыс. Самые длинные инструменты:
`pipe_takeoff` (5,3 тыс. символов), `cable_takeoff`, `drawing_settings`,
`drawing_diff`, `cad_batch`.

В каждом описании есть балласт:
- `meta.cad.synonyms` и `meta.cad.acad` нужны только поиску, но уходят в `tools/list`.
- 240 инструментов объявляют пустой `outputSchema` `{"type":"object","additionalProperties":true}`.
- Параметры вида `z1/z2`, `color`, `linetype` с одинаковыми описаниями повторяются в десятках инструментов.

Ответы инструментов:
- `entity_create_circle` возвращает ≈ 190 символов (полные свойства и bbox), а агенту нужен только handle.
- `entity_list` на 32 объекта занимает ≈ 6 200 символов, примерно 190 на объект.
- `drawing_understand` занимает ≈ 3 800 символов на почти пустом чертеже.
- `view_screenshot` (ezdxf) рендерит PNG 1600×900 (`figsize=(16, 9), dpi=100`). Изображение тарифицируется
  по пикселям (≈ ширина × высота / 750, длинная сторона ужимается до 1568 px), поэтому кадр стоит
  **≈ 1 850 токенов**. На COM захватывается всё окно AutoCAD, обычно ещё крупнее.

Скилл `autocad-spds`: ≈ 47 КБ, грубо 15–20 тыс. токенов на каждую сессию со СПДС.
Почти весь его объём — библиотека AutoLISP `spds:*` и описания обходов багов.
Это и есть «налог» за отсутствие нативных инструментов.

## Этап 0. Измерительный стенд (до любых изменений)

Без замеров не видно, что дала каждая доработка.

- `scripts/measure_context.py`: поднимает сервер in-process через `fastmcp.Client`
  и печатает таблицу «конфигурация → число инструментов → символы/токены каталога».
  Конфигурации берутся из переменных окружения и будущего `TOOL_CONFIG`.
  Если есть `anthropic` и ключ, токены считаются через `count_tokens`, иначе символы / 4.
- Сценарии ответа: несколько типовых последовательностей (создать 30 объектов,
  `entity_list`, digest, diff, скриншот) с суммой символов ответов и пикселей изображений.
- `tests/test_context_budget.py`: регресс-гейт. Каталог профиля `lean` и профиля
  `spds` не должен превышать заданный бюджет, ответ `entity_create_*` в compact-режиме —
  N символов. Бюджеты фиксируются по факту после этапа 1 и дальше только снижаются.
- Результаты кладутся в `benchmarks/results/context/` (JSON), по аналогии с A/B-отчётами.

**Готово, когда:** таблица выше воспроизводится одной командой, а гейт входит в `pytest`.

## Этап 1. Профили и сжатие каталога (пункт 5 Cowork, расширен)

Самый большой и самый дешёвый выигрыш: десятки тысяч токенов на сессию, и
ни одной новой CAD-логики.

### 1.1 Файл профиля `TOOL_CONFIG`

Сейчас есть `TOOL_PROFILE=lean|full` и `TOOL_PACKS=…`. Шестерни, шпонки, GD&T и
3D при этом входят в `core`, и выключить их нельзя.

- `TOOL_CONFIG=path/to/profile.toml` (или имя встроенного пресета):
  ```toml
  packs   = ["core", "spds"]
  exclude_groups = ["gear", "keyway", "gdt", "solid"]   # по тегам
  exclude = ["titleblock_apply_iso_a3"]                 # отдельные инструменты
  include = ["layout_create", "viewport_create"]        # точечно вернуть
  descriptions = "short"                                # см. 1.2
  responses = "compact"                                 # см. 2.3
  ```
- Новые паки вынимаются из `core`: `gear` (`gear_*`, `keyway_*`), `gdt`
  (`gd_frame`, `datum_feature`). `solid` уже управляется `ENABLE_3D`.
- Встроенные пресеты в `config/profiles/`:
  - `spds`: строительные чертежи по ГОСТ. Черчение, слои, блоки, размеры, листы и
    видовые экраны, стили, digest и diff, пак `spds`. Без mech, pid, arch, plant, gear, gdt, solid.
  - `drafting`: универсальное 2D-черчение.
  - `review`: только чтение (understand, digest, diff, critique, screenshot).
  - `full`: как сейчас.
- `system_about` отчитывается об активном профиле и о том, что выключено.
  `call_tool` на выключенный инструмент возвращает понятный отказ с именем профиля
  (механизм `unknown_tool` уже есть).
- Обратная совместимость: `TOOL_PROFILE` и `TOOL_PACKS` продолжают работать, а
  `TOOL_CONFIG` применяется поверх них.

### 1.2 Короткие описания `descriptions = "short"`

- Описание инструмента сокращается до `cad_tool.summary` (одна строка уже есть у
  каждого инструмента) плус обязательные предупреждения. Полный docstring отдаётся
  по запросу: `system_tool_help(name)` или ресурс `autocad://tools/{name}`.
- Описания параметров укорачиваются. Повторяющиеся (`layer`, `color`, `linetype`,
  `z1/z2`) сводятся к одному слову, а соглашение (ACI, WCS, мм) объясняется один раз
  в `instructions` сервера.
- `meta.cad` (`synonyms`, `acad`) и пустой `outputSchema` убираются из `tools/list`
  в любом режиме, кроме `full-debug`. Поиск продолжает их использовать на стороне
  сервера.
- Ожидаемый эффект: −50…60 % к каталогу любого профиля. Проверить замером этапа 0.

### 1.3 Гибридное обнаружение `DISCOVERY_MODE=hybrid`

Профиль (например `spds`) публикуется полностью, а всё остальное доступно через
`search_tools`/`call_tool`. Агент видит частые инструменты сразу и не теряет
редкие.

- Русские синонимы в `discovery/aliases.py`: «отметка», «штамп», «рамка»,
  «ось», «выноска», «штриховка», «слой», «размер», чтобы поиск работал на
  русских запросах.

**Готово, когда:** профиль `spds` в режиме `short` занимает не больше ≈ 8–10 тыс.
токенов (против 93,5 тыс. сейчас), а все существующие тесты профилей и паков зелёные.

## Этап 2. Обратная связь без скриншотов (пункты 1 и 2 Cowork)

### 2.1 `drawing_digest`: компактная сводка состояния

Основная замена скриншоту после серии операций. Только чтение.

Параметры:
- `scope`: `model` | имя листа | `window=(x1,y1,x2,y2)`;
- `layers`: фильтр;
- `checks`: набор проверок (по умолчанию все дешёвые);
- `max_chars`: бюджет ответа (по умолчанию ≈ 1 500), при переполнении сначала
  урезаются списки;
- `format`: `text` (по умолчанию, плотная таблица) | `json`.

Состав:
- количество объектов по слоям × типам (одна строка на слой);
- габариты: объявленные и робастные, плюс handle'ы выбросов (движок уже есть в
  `engineering/understand`);
- предупреждения, каждое с числом и не более 5 handle'ами:
  - незамкнутые контуры: полилинии на контурных слоях, концы отрезков с зазором
    меньше допуска (движок `drawing_topology_check`);
  - пересечения и наложения: `topo_*`, `duplicate_entities`;
  - объекты вне рамки: прямоугольник рамки берётся из XDATA `sheet_frame`/`spds_sheet`
    или из самого крупного прямоугольника на слое рамки. На листе — вне видовых
    экранов и поля рамки;
  - тексты с высотой вне ряда ГОСТ 2.304 / ISO 3098 (с учётом масштаба);
  - веса линий вне ISO 128 / ГОСТ 2.303, объекты на слое `0`, на `CONSTRUCTION`, на `_OUT`;
  - нулевые объекты (отрезок нулевой длины, пустой текст).
- Строка состояния: несохранённые изменения, активное пространство, текущий слой, стили.

Реализация: один снимок (`engineering/understand/snapshot.py`) на вызов. На COM
это `Document.Export` → DXF, без поштучного обхода через COM, который медленный.
Новый модуль `engineering/digest.py`, проверки переиспользуют `critique` и `topology`.

### 2.2 `checkpoint` / `diff_since`: разница с контрольной точки

- `checkpoint(name="default")` запоминает в бэкенде `$HANDSEED` и отпечатки
  объектов: handle → (тип, слой, хэш геометрии и ключевых свойств, округлённый до `tol`).
- `diff_since(name="default", limit=50, fields=…)` возвращает `added` / `modified` /
  `deleted` компактными строками (handle, тип, слой, bbox или ключевое значение) и
  краткую сводку. Для `modified` указываются только изменившиеся поля.
- Опция `auto_checkpoint=true`: `diff_since` сразу ставит новую точку, и цикл
  «действие → дельта» не требует лишних вызовов.
- Отпечатки строятся тем же снимком, что и digest. Сравнение переиспользует
  `engineering/understand/diff.py`; `drawing_diff` сейчас работает только по путям
  к файлам. Новые объекты определяются по handle > `HANDSEED`, это дёшево; изменения —
  по хэшу.
- Точки живут в памяти сессии. Откат транзакции, `drawing_open` и `document_activate`
  делают их недействительными с понятной ошибкой, а не с ложным диффом.
- Каждый изменяющий инструмент в compact-режиме может возвращать `rev` (счётчик
  изменений). Агент видит, что что-то поменялось, не запрашивая дифф.

### 2.3 Компактные ответы `responses = "compact"`

- `entity_create_*`, `entity_copy/move/...` → `{"handle":"5C"}` (+ `handles` для
  массивов), без свойств и bbox. Полный ответ остаётся при `verbose=true` или в профиле `full`.
- `entity_list`: по умолчанию `compact` и столбцовый формат
  (`{"cols":[...],"rows":[[...],...]}`) вместо массива словарей. Это даёт ≈ 3× меньше
  на тех же данных.
- `cad_batch`: в compact-режиме массив handle'ов и только ошибки.
- Числа округляются до точности чертежа (`LUPREC`/`tol`): `100.0` вместо
  `100.00000000001`.

**Готово, когда:** сценарий «создать 30 объектов → проверить результат» стоит в
3–5 раз меньше токенов, чем «30 полных ответов + скриншот», и это подтверждено замером.

## Этап 3. Дешёвые скриншоты (пункт 3 Cowork)

Важная поправка: токены изображения зависят от **пикселей**, а не от формата.
JPEG и ч/б уменьшают трафик и делают линии контрастнее, но экономию токенов даёт
размер кадра: 800×450 стоит ≈ 480 токенов, 600×340 — ≈ 270 токенов, против
≈ 1 850 сейчас (в 4–7 раз меньше).

Параметры `view_screenshot` и `view_zoom_and_screenshot`:
- `window=(x1,y1,x2,y2)` в координатах чертежа: обрезка без изменения
  пользовательского вида. На COM: сохранить вид, zoom, захват, вернуть вид;
  на ezdxf: границы рендера;
- `width` (по умолчанию **800**, диапазон 200–1568), высота по пропорции окна;
- `mode`: `color` | `mono` (чёрные линии на белом) | `gray`;
- `format`: `png` | `jpeg` (+ `quality`, по умолчанию 70); для `mono` разумнее `png`;
- `layers`: показать только эти слои (ezdxf: фильтр рендера; COM: временная
  заморозка с восстановлением);
- `space`: `model` | имя листа.

Дополнительно:
- **Офскрин-рендер для COM**: `render="snapshot"` рендерит снимок `Document.Export`
  через ezdxf/matplotlib. Не зависит от видимости окна, панелей и тёмного фона
  AutoCAD и даёт одинаковую картинку на обоих движках.
- `view_screenshot_tiles(window, cols, rows, width)` для мелких деталей (скилл сейчас
  клеит плитки вручную в Python). Возвращает плитки или одно склеенное изображение.
- Значения по умолчанию задаются из профиля (`screenshot.width`, `screenshot.mode`).

**Готово, когда:** скриншот по умолчанию стоит не больше 500 токенов, а окно в
координатах чертежа одинаково обрезает картинку на обоих движках (тест на ezdxf,
smoke-скрипт на COM).

## Этап 4. Пак `spds`: макросы ГОСТ/СПДС одним вызовом (пункт 4 Cowork)

Сейчас каждый элемент СПДС требует загрузки LISP-библиотеки в документ, `entmake`
и чтения результата через `_OUT`. Каждый макрос ниже заменяет 5–30 вызовов и
большую часть скилла.

Правила репозитория остаются в силе:
- таблицы **транскрибируются** с `SOURCE` (стандарт, редакция, таблица или
  приложение), а размер вне покрытия отклоняется по имени;
- оба движка; слои создаются до первого объекта (правило live ActiveX);
- результат пишется блоками с атрибутами и XDATA `ACADMCP_SPDS`, чтобы его можно
  было прочитать и обновить, а не перерисовывать.

Модуль `engineering/spds/` (`standards/`, `sheet.py`, `marks.py`, `critique.py`).

Общие доработки, без которых макросы неудобны (полезны и вне СПДС):
- `entity_create_text` / `mtext`: параметры `style`, `align` (`TL…BR`, `MC`) и `width_factor`.
- `dimension_*`: параметр `dimstyle=` (сейчас берётся только текущий *сохранённый* стиль).
- Числа с десятичной запятой: `decimal_separator=","` в размерах и отметках.

Проверки: фокусы критики `spds_*` работают под `focus=None` и внутри
`drawing_finalize`, на чертеже без СПДС-записей ничего не возвращают:
- `spds_text_height` — высота вне ряда 2,5/3,5/5/7/10/14/20 на бумаге;
- `spds_lineweight` — веса вне ГОСТ 2.303;
- `spds_axis_letter` — запрещённые буквы, нарушен порядок марок;
- `spds_elevation_format` — формат отметки;
- `spds_stamp_incomplete` — пустые обязательные графы 1, 2, 4, 6, 7;
- `spds_outside_frame` — общий с digest.

Пресет `drawing_apply_standard("gost")` вызывает `spds_setup` для указанного масштаба.
Шаблон `gost_a3_spds` (DXF + `.dwt`) добавляется к `drawing_template_list`.

**Готово, когда:** лист А3 со штампом формы 3, сеткой осей 4×3, тремя отметками и
выноской собирается за ≤ 6 вызовов без `system_run_lisp`. `drawing_critique(focus=None)`
чистый. Smoke-скрипт `scripts/smoke_spds_com.py` прогнан на живом AutoCAD (рус.).

## Этап 5. Баги и узкие места COM, найденные скиллом `autocad-spds`

Скилл писался на AutoCAD 2024 (рус.) и версиях коннектора до 1.6.0. Часть пунктов
могла быть исправлена в 1.6.0: `system_get_variable` теперь читает через
`Document`, а не через `Application`. Поэтому первый шаг — **проверить каждый
пункт вживую** и закрыть то, что осталось. Каждый обход в скилле — это лишние
вызовы и токены.

| # | Симптом из скилла | Что сделать |
|---|---|---|
| 5.1 | `system_run_lisp` не возвращает значение (`nil`/`OK`) | Проверить путь `USERS1` в `com_backend.system_run_lisp`. Вероятные причины: `vl-princ-to-string` от многострочного значения, лимит длины `USERS1`, локализованный AutoCAD. Нужен тест на длинный результат и кириллицу |
| 5.2 | `system_get/set_variable`, `drawing_settings` падали на `Application.GetVariable` | Проверить на 1.6.0. Если исправлено, убрать обход из скилла |
| 5.3 | `entity_create_text` без стиля и выравнивания | См. этап 4 (общие доработки) |
| 5.4 | Размеры игнорируют `setvar`-переопределения | Параметр `dimstyle=` + `dimstyle_create` из пресета ГОСТ |
| 5.5 | AutoCAD создаёт видовой экран по умолчанию на новом листе | `viewport_create(remove_default=True)` и `layout_create(no_default_viewport=True)`; `viewport_list` помечает экран по умолчанию |
| 5.6 | `entity_edit_geometry` умеет только LINE/CIRCLE/ARC | Расширить на LWPOLYLINE (вершины по индексу), HATCH (контур), смещение текста размера (флаг 70 бит 128) |
| 5.7 | `drawing_close` возвращает «Вызов был отклонён», хотя закрыл | Ретрай `RPC_E_CALL_REJECTED` с проверкой `Documents` и честный итог |
| 5.8 | Обрывы связи, `<unknown>.Count` | Классифицировать как `transient`, автоповтор один раз внутри `_run` для операций только на чтение |
| 5.9 | `ALLOWED_PATHS` и несуществующая папка | Ошибка с готовой подсказкой; опция `create_parent=True` внутри разрешённого корня |
| 5.10 | `system_run_command` с многострочным диалогом зависает | Документировать в docstring: «одна команда за вызов». Где возможно, дать нативный инструмент |

## Этап 6. Скилл и инструкции

- Переписать скилл `autocad-spds` под нативный пак: убрать библиотеку `spds:*` и
  разделы обходов. Оставить нормативные требования (кратко, со ссылками на ГОСТ),
  порядок работы и чек-лист. Цель: 47 КБ → ≈ 6–8 КБ.
- Короткие `instructions` сервера, отправляются один раз: соглашения (WCS, мм,
  ACI, handle'ы), цикл «действие → `diff_since`/`digest` → скриншот только в конце
  этапа», `cad_batch` для серий.
- Ресурс `autocad://guide/workflow` с полной версией для тех, кто захочет её прочитать.

## Порядок и оценка

| Этап | Выигрыш | Объём | Риск |
|---|---|---|---|
| 0. Стенд замеров | основа для всего | S | низкий |
| 1. Профили + короткие описания | **−80…90 % каталога** (93 тыс. → ~10 тыс.) | M | низкий: не трогает CAD-логику |
| 2. digest + checkpoint/diff + compact | −60…80 % на цикл проверки | M–L | средний: COM-снимок на больших чертежах |
| 3. Скриншоты | −75…85 % на кадр | S–M | низкий |
| 5. Баги COM | меньше шагов и ретраев | M | нужен живой AutoCAD |
| 4. Пак `spds` | −15…20 тыс. токенов скилла + 5–30 вызовов на элемент | L | средний: транскрипция ГОСТ, оба движка |
| 6. Скилл и инструкции | закрепляет эффект | S | низкий |

Рекомендуемая последовательность PR: **0 → 1 → 3 → 2 → 5 → 4 → 6**. Этапы 1 и 3
быстро дают ощутимую экономию. Этап 2 зависит от снимка и определяет формат
ответов для пака `spds`. Этап 5 стоит начать до пака `spds`: те же места (тексты,
размерные стили, видовые экраны) нужны макросам.

Каждый PR по правилам репозитория:
- контракт в `backends/contracts/`, реализация в обоих движках, `@capability`
  только для настоящей границы движка, ключ объявлен в обеих картах;
- регистрация в `server.py` с `@cad_tool(summary=…, cost=…)` и тегами пака;
  алиасы в `discovery/aliases.py` (гейт покрытия);
- тесты на ezdxf + fake-COM; smoke-скрипт для живого AutoCAD там, где есть COM-путь;
- `CHANGELOG.md`, разделы `CLAUDE.md`/`README.md`; числа инструментов не
  хардкодятся (`scripts/check_doc_numbers.py`);
- версия: этапы 0–3 → 1.7.0, пак `spds` → 1.8.0.
